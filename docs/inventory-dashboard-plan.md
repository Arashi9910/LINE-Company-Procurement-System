## 步驟

1. ~~**確認飛鼠訂單 API 的未知項目**~~ ✅ **已完成（2026-10-29）**
   - 狀態 0＝處理中、2＝備貨中，已確認。
   - `part_list[].qty` 是每 1 件的用量，**沒有**乘過購買數量，要自行乘上 `products[].qty`。
   - 翻頁用 `offset`，`pageCode` 不生效；`size` 未發現上限，用 200。
   - 另查出三個陷阱：不可帶日期條件、沒有 `part_list` 的列要跳過、`columns[]` 和 `detail=1` 都不能少。
   - 結果已記錄在規格第 7 節。

2. **`src/flyingmouse/order-reader.js`**（本輪要做的）

   介面：`createFlyingMouseOrderClient(page)` 與純函式 `aggregateOrderQuantities(ordersByStatus)`，
   讓翻頁／HTTP 歸客戶端，數量計算歸純函式，測試不需要真的瀏覽器。

   **查詢條件（依規格第 7 節實測，不可更動）：**
   ```
   GET /api/admin/order?detail=1&equals[deleted]=0&equals[status]=<0|2>
       &columns[]=id&columns[]=no&columns[]=status&offset=<n>&size=200
   ```
   - 翻頁一律用 `offset` 累加 `size`，**不可送 `pageCode`**（實測不生效，會無限抓第 1 頁）。
   - **不可送 `gtes[create_time]` / `ltes[create_time]`**，否則會漏掉兩個月前的預購單（實測 87 vs 97）。
   - `detail=1` 與 `columns[]` 都不可省略。
   - 狀態 9「待取消/退貨」**本輪不計入**，等規格第 8 節的人工觀察有結論再處理。

   **數量計算：**
   - 某貨號數量 `+= products[].qty × part_list[].qty`。
   - `part_list` 為空的商品列（折價列等）**直接跳過，不可視為錯誤**；不可用 `product_type` 判斷。
   - 一列有多個貨號（組合包）要各自累加；目前實測沒有，仍要寫成通用迴圈。

   **回傳：** 每個貨號的 `{ processing, preparing, total }`（狀態 0／狀態 2／兩者相加）。

   **完整性檢查（光比對筆數不夠）：**
   - 以**訂單 id 去重後的數量**核對 `data.total`，不是累計列數。重複頁會讓列數剛好但內容少一半。
   - 每一頁回傳的 `data.total` 必須一致，中途變動代表資料在動，要重讀。
   - 每筆訂單的 `status` 必須等於查詢的狀態，不符就是漂移。
   - **跨狀態去重**：狀態 0 與 2 分兩次查，同一張單可能在兩次查詢之間從 0 轉成 2 而被算兩次。
     以訂單 id 為鍵跨狀態去重，重複者以**後查到的狀態**為準並記錄一次警告。
   - 不一致時最多重讀 2 次；仍不一致就丟錯，由呼叫端保留上一次看板（規格第 5 節）。

   **失敗處理：**
   - HTTP 非 2xx、回應格式不正確、`part_list` 內貨號空白或數量非正整數，都要丟出可辨識的錯誤。
   - 迴圈要有上限，避免 `offset` 沒前進時無限打 API。

   **驗收：**
   - `test/flyingmouse-order-reader.test.js` 用假的 `page` 覆蓋：多頁翻頁、`products.qty=2` 要乘出 2、
     跳過無 `part_list` 的列、組合包、筆數不符、HTTP 錯誤、空清單，
     以及**重複頁（列數對但 id 重複）**、**回傳狀態與查詢不符**、**同一訂單同時出現在狀態 0 與 2**。
   - 乾跑一次真資料，狀態 0 與 2 的筆數要等於 API 的 `data.total`，
     並與 2026-10-29 的基準（97／1 筆、184 件、57 個貨號）同量級。

   - 加一支腳本 `scripts/setup-inventory-dashboard.mjs`，用來建立這兩個分頁和表頭。

     分成「寫入」與「清除」兩次請求的話，中間失敗會留下新舊混合的看板

5. ~~**接進每小時的排程**~~ ✅ **已完成（2026-10-29）**

   新增 `src/services/inventory-dashboard-job.js`（IO 與失敗處理）、
   `scripts/flyingmouse-dashboard.mjs`（CLI 與飛鼠 session），
   並把看板接成 `flyingmouse-combined-job.mjs` 的第三階段。
   同步狀態另開「看板同步狀態」分頁（規格第 4.3 節），
   因為「庫存看板」每輪整張覆寫會把它蓋掉。
   乾跑（攔截所有寫入）：1447 列、回寫未完成 5 個、兩筆寫入分別是
   `'庫存看板'!A1:N1448` 與 `'看板同步狀態'!A2:D2`。


   **看板必須排在回寫「之後」，不是之前。**
   `src/sheets/repository.js` 在登記到貨當下就把補貨追蹤的到貨量加上去、未到量減掉，
   但飛鼠庫存要等 `completeWritebackEvent` 才寫進 SKU主檔的庫存快照
   （`sheets-writeback.js` 寫 `MAIN_SHEET_NAME!E{row}`）。
   夾在中間跑的話，「已叫貨未到」已經歸零而「飛鼠庫存」還沒加上去，缺口會被高估。
   以規格的商品 A 為例：5 件已登記到貨但還沒回寫，看板會算出缺口 3，正確值是 −2，
   而且這個錯誤會留到下一小時，觸發多餘的叫貨提醒。

   - 順序改成：商品同步 → 回寫 → **看板**。
   - 看板步驟要**重新讀取**庫存快照與補貨追蹤，不可重用回寫前讀到的值。
   - **只要該 SKU 還有任何 `status !== '已完成'` 的回寫事件，缺口就不發布也不提醒**，
     在狀態欄標成「回寫未完成」，避免用半套資料叫貨。
     實際狀態值見 `sheets-writeback.js` 的 `WRITEBACK_STATUSES`：
     `待處理`、`已準備`、`等待重試`、`已完成`、`需人工確認`——
     要擋的是除了「已完成」以外的全部四種。
   - **要讀完整的回寫事件清單，不可用 `listProcessableWritebacks`**：
     它會跳過 `nextRetryAt` 還沒到期的「等待重試」、不回「需人工確認」，
     而且有 `limit` 批次上限（預設 20），代表不了「所有未完成的回寫」。
   - 驗收案例：重試尚未到期、需人工確認、已準備、未完成事件數超過批次上限，
     這四種情況下該 SKU 都必須被擋下。

   **失敗處理要對齊規格第 5 節**（原本寫「只記錄錯誤」不符）：
   - 看板失敗時**不覆寫**既有的「庫存看板」分頁，保留上一次的數值與最後成功時間。
   - 另設同步狀態欄位，失敗時寫入「同步失敗」與錯誤摘要。
   - 同步失敗期間**停止叫貨提醒**，`查缺貨`／`查庫存` 要在回覆開頭標明資料為上一次成功的結果與時間。
   - 看板失敗仍不可影響商品同步與回寫的結果。

   - 用環境變數 `INVENTORY_DASHBOARD_ENABLED` 控制開關，預設關閉。

6. **LINE 提醒和指令**

   **指令要同時接進 webhook，只加解析不夠。**
   `src/routes/webhook.js:161` 對所有沒被前面分支接住的 command，一律走
   `listRequestRows` → `summarizeRequests` → `replyStatusCards`。
   `查缺貨`／`查庫存` 若只加在 `group-commands.js`，會掉進補貨狀態查詢，回不出庫存。
   - 在 `src/services/group-commands.js` 加 `查缺貨` 和 `查庫存` 的解析。
   - 在 `webhook.js` 於既有分支之間加上明確分派，沿用現有的群組授權檢查。
   - 驗收要有一條從 LINE 事件進、庫存回覆出的整合測試。

   **去重規則：用「當天已提醒過的缺口基準」，不是「日期＋SKU＋缺口」。**
   規格第 4.4 節是「同一天只提醒一次，除非缺口又變大」。
   把缺口放進鍵值的話，10 → 5 會產生新鍵而再推一次；
   `reminders.js` 與 `repository.reserveReminder` 只看鍵存不存在，不比大小。
   - 每天每個 SKU 記錄一個「已成功提醒的缺口基準」。
   - 只有當天第一次、或缺口**大於**該基準時才預約推播；推播成功後把基準更新成新缺口。
   - 推播失敗要能重試（沿用先預約、失敗還原的機制），不可因為預約過就再也不提醒。
   - 驗收案例：10 → 5 不提醒、10 → 12 要提醒、推播失敗後重試會成功、跨日重置。

   **只通知動銷中的 SKU（使用者決定，2026-10-29，見規格第 2.1、4.4 節）。**
   老闆的要求是「近一個月有在動的才通知，其他的他自己判斷」。
   新品上架時預購額度一律先填 10，所以測試品賣出第一筆就會算出缺口——
   數字沒錯，但不該推播。
   - 判定：**近 30 天內有訂單就算動銷，不看件數**。
   - 看板分頁照列全部，篩選只作用在推播。
   - 動銷清單在推播當下另外查飛鼠訂單，不寫進看板欄位。
   - **實作前要先實測日期參數**：規格第 7.5 節記錄「送 `gtes[create_time]`
     會讓筆數從 97 掉到 87」，當時的結論是查未寄訂單不可帶日期；
     查動銷正好需要帶，但語意還沒確認。若日期參數不可靠，
     退路是抓全部未取消訂單後在本地依 `create_time` 篩。
   - 驗收案例：測試品只賣出 1 件（30 天內有訂單）要通知；
     半年沒出單但缺口為正的不通知；動銷判定失敗時不可整批停推，要記錄並照舊推播。

   - 加一個 Scheduler 端點，推播時間等老闆決定。

7. **驗證**
   - `npm test`、`npm run lint`、`npm run build` 都要通過。
   - 用正式資料乾跑一次，產出看板預覽，人工抽查 5 個 SKU，跟飛鼠後台比對。

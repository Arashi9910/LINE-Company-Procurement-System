# 銷售商品名稱同步規格

## 1. 問題

飛鼠有兩層名稱，而且兩層都是「現況」，內容會不一樣：

| 層級 | 誰在維護 | 例子（同一貨號、同一時刻） |
| --- | --- | --- |
| 貨品（part） | 建檔當下寫入，之後不會跟著改 | `預售✨ BTS防彈少年團應援棒收納盒 …` |
| 銷售商品（product） | 上架時維護，前綴會隨供貨狀況改 | `隔日到貨⚡️BTS防彈少年團應援棒收納盒 …` |

2026-10-30 以同一個登入、同一時刻分別打 `/api/admin/product/part/…` 與
`/api/admin/product/{productId}` 驗證，確認差異不是同步落後，而是兩個獨立欄位。
另外 `297903` 的貨品已回 HTTP 404、銷售商品仍存在，貨品層連「存不存在」都不保證。

官方 Excel 匯出的是**貨品層**，SKU主檔 因此一路沿用舊名稱：

- SKU主檔 1625 列，**215 列**的補貨顯示名稱前綴與銷售商品不一致。
- 補貨追蹤 469 列，**237 列**的「品項」已過時；其中還在流程中
  （待確認／已下單／部分到貨）的 54 列裡有 **20 列**過時，
  **11 列**是「單上寫預購、實際早就是現貨」。
- 庫存看板 1458 列裡 **174 列**的現貨／預購分類會翻掉，其中 53 列近 30 天有銷量。

對採購的實際後果：單子上寫「預購」，採購以為還在等上游，於是重複下單；
或是看到「預購」就不去追到貨。這比看板數字錯更嚴重，因為它直接導致重複叫貨。

## 2. 正確的來源

每小時的 `flyingmouse-sync` 已經在掃飛鼠貨品列表，並把**銷售商品名稱**寫進
「商品圖片對照」的 E 欄。這份資料：

- 由 `syncProductImages` 每小時比對一次，`商品名稱` 屬於受管欄位。
- 「擷取時間」欄被 `sameManagedValues` 刻意排除在比對之外，所以它的語意是
  「最後一次有變動」而不是「最後一次檢查」。名稱沒改過的列會一直留著舊時間戳，
  這不代表資料過期。
- 一個貨號對到多個銷售商品時，分類衝突數為 0（2026-10-30 全量檢查）。

因此本規格不增加任何飛鼠端的負擔，只是把既有資料接到正確的位置。

## 3. 不能動的地方

`src/flyingmouse/sheets-baseline.js` 的 `loadReferenceCatalogFromSheet` 讀
SKU主檔 `A2:D`（SKU、商品名稱、規格1、規格2）當作與官方 Excel 比對的基準。

> **SKU主檔 B 欄「商品名稱」必須維持貨品層的值。**
> 若改寫成銷售商品名稱，每一列都會被判定為與 Excel 不符，差異報告永遠爆掉。

## 4. 修改內容

### 4.1 補貨顯示名稱改用銷售商品名稱

`syncCatalogToSheet`（auto 模式，每小時執行）本來就會改寫 SKU主檔 的 `B:H`，
其中 H 欄是 `buildDisplayName(source)` 產生的。把它改成：

```
補貨顯示名稱 = （銷售商品名稱 ?? 貨品商品名稱）｜規格1｜規格2
```

銷售商品名稱來自同一輪 `captureFlyingMouseProductList` 的結果，以貨號比對。
查不到時沿用貨品名稱，不中斷同步。

`catalogSku` 的 `displayName` 本來就優先取 H 欄，所以 LINE 補貨單、庫存看板、
`查缺貨`、`classifyStockMode` 會同時拿到正確名稱，不需要各自改。

`sheets-review.js` 的匯入路徑（新 SKU 首次寫入）維持現狀，
下一輪 `syncCatalogToSheet` 會在一小時內把 H 欄補正。

### 4.2 SKU主檔 新增「出貨型態」欄

MAIN_HEADERS 由 14 欄擴為 15 欄，新增 O 欄「出貨型態」，值為
`現貨`／`預購`／`未知`，由 `classifyStockMode` 以銷售商品名稱推導，
與 H 欄在同一輪寫入。

目的是讓採購不必從 40 字的標題裡找前綴，也避免前綴出現新寫法時沒人察覺。

庫存看板改讀這一欄，而不是自己再推導一次，確保兩邊不會各算各的。

### 4.3 補貨追蹤 新增「出貨型態」欄並刷新在途單

TRACKING_HEADERS 末端新增 W 欄「出貨型態」，`TRACKING_LAST_COLUMN` 由 `V` 改為 `W`。

每小時同步時，對狀態為 **待確認／已下單／部分到貨** 的列：

- 以該列的 SKU 查目前的補貨顯示名稱，與 D 欄「品項」不同時更新 D 欄。
- 一併寫入 W 欄「出貨型態」。

狀態為已到貨、取消等已結案的列**不更動**，保留當初下單時的名稱作為紀錄。

無法在 SKU主檔 找到對應貨號的列跳過，不報錯。

#### 與 LINE 端寫入的競爭

這支跑在獨立的同步 Job，與 LINE 的寫入不同程序，`SheetsRepository` 的寫入佇列
保護不到。危險的交錯是：到貨時若帶規格修正，repository 會改寫同一列的
D（品項）、N（SKU）並把狀態推進成已完成。若刷新接著把**讀取當下**那個舊 SKU 的
名稱寫回 D，就會變成 N 是新 SKU、D 是舊名稱，而該列已結案、往後不再刷新，
錯誤永久留著。

因此：**有東西要寫時，先重讀一次補貨追蹤，並完全依最新那份重算要寫什麼。**
中途被改過的列，要嘛已經不在流程中而被排除，要嘛算出來的是配著新 SKU 的名稱。

殘留風險：重讀到送出之間那一瞬仍可能被插入。要完全消除得靠所有寫入者共同遵守的
跨程序鎖，那會牽動 repository 的每一條寫入路徑，不在本次範圍。

### 4.4 表頭遷移

SKU主檔 與 補貨追蹤 的表頭檢查是嚴格比對（`exactHeaders`），
正式環境的兩張分頁必須先補上新欄位，程式才能部署。
提供 `scripts/setup-sales-name-sync.mjs`，負責：

- 檢查並擴充欄數。
- 寫入新表頭，若既有表頭已正確則不動作（可重複執行）。
- 不清除任何資料列。

## 5. 驗收

- `npm test`、`npm run lint`、`npm run build` 全過。
- 新增測試涵蓋：
  - 銷售商品名稱存在時 H 欄用它、不存在時回退貨品名稱。
  - SKU主檔 B 欄在同步後仍等於 Excel 的貨品名稱（防止 §3 的回歸）。
  - 補貨追蹤只更新在途列，已結案列不被改寫。
  - 表頭遷移腳本可重複執行且不動資料。
- 以正式試算表實跑一次 dry-run，確認：
  - SKU主檔 預期更新列數落在 215 列附近。
  - 補貨追蹤 預期更新列數為 20 列（在途且名稱過時）。

## 6. 風險

- **一個貨號對到多個銷售商品**：目前衝突數為 0，但未來可能出現。
  `syncProductImages` 已有 `銷售商品綁定JSON` 欄位記錄多重綁定；
  取名稱時固定取第一個綁定，並在分類不一致時記為「未知」，不猜。

  出貨型態必須與名稱**在同一處一起決定**，不可以讓呼叫端從最後的顯示名稱回推：
  衝突時顯示名稱只代表其中一個綁定，拿它重新分類等於把「不知道」偷換成一個猜測。
  貨品層的名稱本身也常帶前綴，回退時同樣不能拿來當分類依據。
- **改寫在途單的品項**會讓該列與當初下單時看到的文字不同。
  這是刻意的取捨：採購需要的是現況而非存檔。已結案列不動即為補償。

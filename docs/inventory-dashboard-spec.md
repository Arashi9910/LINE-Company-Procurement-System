# 庫存看板與叫貨提醒規格（第 0 階段）

更新：2026-10-28｜狀態：待審查｜範圍：只讀取飛鼠，不寫入、不改動飛鼠

## 1. 要解決的問題

老闆看不到「實際有幾個、賣掉還沒寄幾個、已經叫貨還沒到幾個」，所以叫貨總是晚好幾天。預購商品的庫存欄同時被拿來當可賣數量，每次都要人工重算再覆蓋，帳一直對不起來。

## 2. 名詞與資料來源

| 名詞 | 定義 | 來源 |
|---|---|---|
| 飛鼠庫存 | 飛鼠後台顯示的庫存。飛鼠下單時就扣、取消會補回。**超賣時會是負數，負值是真實值，不夾成 0**（見第 9 節） | 每小時同步到「SKU主檔」的 `庫存快照` 欄 |
| 賣掉還沒寄 | 狀態為**處理中＋備貨中**的訂單，依 `part_list` 的貨號加總數量 | 飛鼠訂單 API，即時讀取 |
| 已叫貨未到 | 「補貨追蹤」中狀態為「已下單」或「部分到貨」的列，數量為下單量減到貨量；貨號優先用「修正後規格」，沒有才用原 SKU | 補貨追蹤分頁 |
| 預購額度 | 開預購時，在飛鼠庫存裡多放的可賣數量 | 新增「預購額度」分頁，人工維護 |
| 安全庫存 | 至少要留的數量，可以不填，預設 0 | 同上 |
| 動銷 | 近 30 天內有訂單的 SKU，不看件數 | 飛鼠訂單 API，每小時寫進「動銷清單」分頁（見 4.5） |

訂單狀態的意思（使用者確認）：
- **處理中**：大多是預購，已經有人買了，但貨還沒到，也還沒印寄件單。
- **備貨中**：寄件單已經印出，貨已經有了。可能包好還沒寄，也可能已經寄出但蝦皮狀態還沒更新。
- **運送中**：已經寄出，在蝦皮或第三方物流手上。不算在「賣掉還沒寄」裡。

## 2.1 營運模式（使用者說明，2026-10-29）

這段決定了看板與通知的用法，不是背景資訊：

- **開預購是用來測有沒有人買。** 新品上架時預購額度一律先填 10，飛鼠庫存也放 10。
  這個 10 是佔位用的，沒有盤點依據。
- **沒人買就不用管。** 不需要補貨、不需要提醒，放著就好。
- **賣得動才囤貨。** 只有開始頻繁出單的商品才會進貨，這時候預購額度與實際數量才需要校正。
- **新品一直在上架**，所以長尾會持續變大。SKU主檔 1623 支裡，
  2026-10-29 當下有未寄訂單的只有 58 支、有叫貨中的 55 列。

直接後果：**缺口公式對測試品一樣會算出正數**（賣掉 3 件就是真的欠 3 件），
數字沒錯，但那不是老闆想被通知的東西。所以篩選要做在**通知**上，不是改公式。

## 3. 公式

```
推算實際庫存 = 飛鼠庫存 + 賣掉還沒寄 − 預購額度
缺口         = 賣掉還沒寄 + 安全庫存 − 推算實際庫存 − 已叫貨未到
             = 預購額度 + 安全庫存 − 飛鼠庫存 − 已叫貨未到
```

- 缺口大於 0，代表要再叫這麼多個。
- 缺口最後只跟「預購額度、安全庫存、飛鼠庫存、已叫貨未到」有關，**不受訂單狀態分類影響**。所以有些「備貨中」的單其實已經寄出、只是狀態還沒更新，也不會讓叫貨數量算錯，只會讓「推算實際庫存」暫時多算幾個。
- 推算實際庫存小於 0 時，標成「異常」。通常代表預購額度填錯，或飛鼠庫存被人手動改過，要人工檢查。

### 驗算（商品 A，預購額度 10）

| 時間點 | 飛鼠 | 未寄 | 叫貨中 | 推算實際 | 缺口 |
|---|---|---|---|---|---|
| 賣 3 | 7 | 3 | 0 | 0 | 3 |
| 叫 5 | 7 | 3 | 5 | 0 | −2 |
| 到貨 5（現行回寫：7 + 5） | 12 | 3 | 0 | 5 | −2 |
| 寄 3 | 12 | 0 | 0 | 2 | −2 |
| 再賣 3 | 9 | 3 | 0 | 2 | 1 |
| 關閉預購：額度改成 0，飛鼠改成 2 − 3 = −1 | 需要人工處理 | | | | |

最後一列的意思是：還有 3 單沒寄、實際只有 2 個，這時候不能關閉預購。看板要直接顯示「目前不能關閉預購，還差 1 個」。

## 4. 輸出

### 4.1 「庫存看板」分頁（系統每小時整張覆寫，不要手動改）

欄位：SKU、商品名稱、飛鼠庫存、處理中、備貨中、賣掉還沒寄、已叫貨未到、預購額度、安全庫存、推算實際庫存、缺口、狀態（正常／要叫貨／異常／回寫未完成）、**備註**、更新時間。

備註欄放不能用數字表達的事：「目前不能關閉預購，還差 N 個」（第 3 節最後一列）、規格修正失效、SKU主檔查無此貨號、回寫未完成的原因。

狀態是「回寫未完成」時，推算實際庫存與缺口**寫成空白儲存格，不可寫 0**——寫 0 在看板上看起來就是「不缺貨」。備註同理不帶出被壓下來的數字。

排序：要叫貨排最前面，接著是異常，最後是正常；同一類裡缺口大的排前面。只列有庫存、有訂單、有叫貨中，或有填預購額度的 SKU。

### 4.2 「預購額度」分頁（人工維護）

欄位：SKU、預購額度、安全庫存、備註、最後修改人、最後修改時間。

**操作規則：只要在飛鼠為了預購改庫存，就要同步修改這一欄。**

### 4.3 「看板同步狀態」分頁（系統維護）

欄位：狀態、最後成功時間、最後嘗試時間、訊息。只有第 2 列一筆資料。

**不能放在「庫存看板」裡**：那張表每輪整張覆寫，會把它一起蓋掉，
而它存在的意義正是「看板覆寫失敗時還看得到上一次成功是什麼時候」。

- 成功：狀態＝`正常`，最後成功時間與最後嘗試時間都寫這一輪的時間，訊息清空。
- 失敗：狀態＝`同步失敗`，**最後成功時間沿用上一次的值**，訊息寫錯誤摘要。
  錯誤摘要會去換行、遮蔽 password／cookie／authorization／token、限長 300 字。
- 連狀態都讀不到時，最後成功時間寫空白，不可謊報一個時間。

### 4.4 LINE 查詢（不推播）

**不做主動推播**（使用者決定，2026-10-29）。原因是 LINE 官方帳號的免費額度
只算主動推播、不算回覆，而既有的每日待辦已經吃掉不少額度。
叫貨資訊改成「想看就查」：

- `查缺貨`：列出目前要叫貨的 SKU（缺口大於 0 且狀態為「要叫貨」）。
  - **異常另外分一段報**，不可以混在「要叫貨」裡：
    查無貨號、規格修正失效、推算實際為負這三種情況缺口照樣是正的，
    但要人先確認，直接拿去下單就錯了。每一列都要帶完整 SKU 與原因。
  - **只列動銷中的 SKU**（見下）。被篩掉的只報數量，不列出來。
- `查庫存 {SKU 或關鍵字}`：顯示該商品的四個數字、缺口與狀態。
- 同步失敗期間，回覆開頭標明資料是上一次成功的結果與時間。

### 4.5 「動銷清單」分頁（系統每小時整張覆寫）

欄位：SKU、起算日、更新時間。

近 30 天內有訂單的貨號，**不看件數**（使用者決定）。
用來把 `查缺貨` 的長尾濾掉：新品上架一律先填預購額度 10，
賣出第一筆就會算出缺口，但那是測試品，不該跟真正在動的商品混在一起報。

為什麼要存成分頁：只有每小時的 Job 進得去飛鼠（web 映像沒有 Playwright，
也沒有複製 `scripts`），而 `查缺貨` 跑在 web 服務上。這張分頁是兩邊之間的橋。

- 取數涵蓋近 30 天建立的訂單，不限狀態，但**本地排除取消(4)與棄單(6)**；
  待取消/退貨(9)與退貨(8)仍算動過，因為都代表有人真的下過單。
- 日期用 `gtes[create_time]`，已實測可靠（見第 7.5 節）。
  起算日一律以**台北日曆日**回推，不可用主機時區（容器是 UTC）。
- 寫入失敗不可以讓整輪看板變成「同步失敗」——它是附加品，看板數字本身是好的。
- 讀不到時 `查缺貨` **照常回答全部**，不篩選。篩子壞了不該讓人連缺貨都查不到。
  讀取是**獨立一個請求**，不可以跟看板放在同一次 `batchGet`：
  分頁不存在時整個請求會失敗，連 `查缺貨`／`查庫存` 都回不出來。
- **「查過且為空」與「還沒查過」必須分得出來。** 近 30 天真的沒有任何有效訂單
  是合法結果（例如只剩更早的未寄預購單），這時候還是要篩。
  空集合時寫一列「SKU 空白、但有起算日與更新時間」當完成標記；
  只有表頭代表還沒寫過，這時候不篩。
- **只有跟看板同一輪產出的清單才拿來篩。** Job 寫這兩張用同一個時間戳，
  所以 `動銷清單` 的更新時間不等於看板的更新時間，就代表動銷那一步在最新這輪
  失敗了、清單是舊的。拿舊清單去篩會把今天才開始出單的商品誤判成「沒在動」而藏起來。

## 5. 安全與失敗處理

- 第 0 階段**不寫入飛鼠**，只讀取訂單。
- 讀取訂單失敗、分頁不完整、筆數對不上時，**不要覆寫看板**，保留上一次的結果，
  並在「看板同步狀態」分頁記錄失敗與錯誤摘要（見第 4.3 節）。
- 看板步驟**必須排在到貨回寫之後**，而且要重新讀取庫存快照與補貨追蹤。
  repository 在登記到貨當下就把補貨追蹤的未到量減掉，但飛鼠庫存要等
  `completeWritebackEvent` 才寫進 SKU主檔；夾在中間跑的話「已叫貨未到」已歸零
  而「飛鼠庫存」還沒加上去，缺口會被高估並觸發多餘的叫貨提醒。
- 只要該 SKU 還有任何 `status !== '已完成'` 的回寫事件，缺口就不發布也不提醒，
  狀態標成「回寫未完成」。要讀**完整的**回寫事件清單，不可用
  `listProcessableWritebacks`（它會跳過未到期的重試、不回「需人工確認」、還有批次上限）。
- 看板失敗不得影響商品同步與回寫的結果。
- 以 `INVENTORY_DASHBOARD_ENABLED` 控制開關，預設關閉。
- 訂單 API 必須帶 `detail=1`、`equals[status]` 和 `columns[]`。`keyword` 和 `likes` 實測不會篩選，禁止使用。
- 翻頁一律用 `offset`，**不可用 `pageCode`**（實測不生效，會無限抓第 1 頁）。
- 查詢**不可帶 `gtes[create_time]` / `ltes[create_time]`**，否則會漏掉兩個月前的預購單。
- 商品列沒有 `part_list` 時（折價列等）直接跳過，不可視為錯誤。
- 詳細實測結果見第 7 節。
- 「預購額度」分頁的 SKU 不存在於 SKU主檔時，標成異常，不中斷整批處理。

## 6. 上線前的初始校正

1. 列出目前所有預購中的 SKU。
2. 實際清點這些 SKU 的實體數量。
3. 預購額度 = 飛鼠庫存 + 賣掉還沒寄 − 清點數量，寫進「預購額度」分頁。

## 7. 飛鼠訂單 API 實測結果

實測日期：2026-10-29｜方式：Playwright 登入後唯讀乾跑，只送 GET，非 GET 一律攔截

### 7.1 端點與必要參數

```
GET /api/admin/order?detail=1&equals[deleted]=0&equals[status]=0
    &columns[]=id&columns[]=no&columns[]=status
    &offset=0&size=200
```

回應為 `{ data: { total, list }, code, message }`。

- `detail=1` **必要**，沒有就不會回 `products` 和 `part_list`。
- `columns[]` **必要**，沒有的話連 `no` 都是 null。`products` / `part_list` 不受 `columns[]` 影響。
- `keyword` 和 `likes` 實測不會篩選，禁止使用。

### 7.2 訂單狀態代碼（已確認）

| 代碼 | 名稱 | 2026-10-29 全量筆數 |
|---|---|---|
| **0** | **處理中** | **97** |
| **2** | **備貨中** | **1** |
| 3 | 運送中 | 78 |
| 4 | 取消 | 164 |
| 5 | 完成 | 1005 |
| 6 | 棄單 | 0 |
| 7 | 待付款 | 0 |
| 8 | 退貨 | 0 |
| 9 | 待取消/退貨 | 81 |

「賣掉還沒寄」取狀態 **0 和 2**，與原先推測一致。

### 7.3 `part_list[].qty` 是每 1 件的用量，沒有乘過購買數量

實測 11 張購買數 ≥ 2 的訂單，全部都是 `products[].qty = 2`、`part_list[].qty = 1`。
目前全站 172 筆 part 的 qty 都是 1。

```
某貨號的扣帳數量 = products[].qty × part_list[].qty
```

以 2026-10-29 的狀態 0＋2 計算：**184 件、57 個貨號**。

### 7.4 分頁：用 `offset`，不要用 `pageCode`

- **`pageCode` 不會生效。** 只給 `pageCode=2` 不給 `offset`，回傳的仍是第 1 頁。照後台原樣帶 `pageCode` 寫迴圈會無限抓第 1 頁。
- 真正翻頁的是 `offset`，搭配 `size`。
- `size` 試到 5000 都沒被截斷（1425 筆一次全回），未發現上限；仍建議 `size=200` 搭 `offset` 翻頁，避免相依於未定義行為。
- 翻頁完整性已驗證：狀態 0 用 `size=20` 翻 5 頁，去重後 97 筆＝`data.total`，無重複無遺漏。

### 7.5 日期條件：查未寄不可帶，查動銷必須帶

後台預設會塞 `gtes[create_time]` / `ltes[create_time]`，只看近兩個月。

| 查詢 | 狀態 0 筆數 |
|---|---|
| 帶後台預設的兩個月區間 | 87 |
| 不帶日期條件 | 97 |

少掉的 10 張正是放最久的預購單，也最需要叫貨。
**查「賣掉還沒寄」時不可帶日期條件。**

**但參數本身是可靠的**（2026-10-29 實測，狀態 5 全量 1006 筆）：

| 寫法 | API total | 窗外筆數 | 與本地自己數的 268 筆 |
|---|---|---|---|
| `gtes[create_time]=2026-09-29` | 268 | 0 | 相符 |
| `gtes[create_time]=2026-09-29 00:00:00` | 268 | 0 | 相符 |
| 同時帶 `gtes` 與 `ltes` | 268 | 0 | 相符 |

所以當初「97 掉到 87」不是參數壞掉，是**未寄訂單裡本來就有舊的預購單**
（實測當下 60 筆未寄裡有 16 筆超過 30 天）。兩條規則同時成立，不衝突：

- 查「賣掉還沒寄」（狀態 0、2）→ **不帶日期**，否則漏掉舊預購單。
- 查「近 30 天動銷」（第 4.4 節的推播篩選）→ **帶 `gtes[create_time]`**，可靠。

`create_time` 回傳格式是 `YYYY-MM-DD HH:mm`（沒有秒）。

附帶影響：看板的「處理中」數字會比後台分頁標籤上的數字大，這是正確的，不是 bug。

### 7.6 沒有 `part_list` 的商品列要跳過

狀態 0＋2 共 207 個商品列，其中 **35 列沒有 `part_list`**：

| 類型 | 列數 | 說明 |
|---|---|---|
| `type=3` | 21 | 「折價或優惠」，金額為負 |
| `type=1` / `type=2`，無 part | 14 | 沒有對應貨號的列 |

這些要跳過，不可當成錯誤中斷。

**不可用 `product_type` 篩選**：有 7 列 `product_type=null` 但確實有 `part_list`。判斷依據一律是 `part_list` 有沒有內容。

目前沒有組合包（單列最多 1 個貨號），但資料結構允許多筆，實作仍要寫成通用迴圈。

## 9. 飛鼠負庫存

飛鼠超賣時庫存會是負數（例：2026-10-29 的 `260826165824` 是 −1）。
負庫存是**真實值**，代表已出的量比帳上多，整條鏈一律照原值傳遞，不夾、不擋。

### 為什麼不能夾成 0

```
缺口     = 預購額度 + 安全庫存 − 飛鼠庫存 − 已叫貨未到   → 夾成 0 會少算 |負值|
推算實際 = 飛鼠庫存 + 賣掉還沒寄 − 預購額度              → 夾成 0 會多算 |負值|
```

該叫 N 個時只會叫 N−1 個，而且負庫存正是最需要補貨的情況。

### 原本擋負值的五個地方（2026-10-29 全部改掉）

| 位置 | 原本 | 現在 |
|---|---|---|
| `src/flyingmouse/catalog.js` `parseStock` | `Math.max(0, stock)` | 原值帶出 |
| `src/flyingmouse/sheets-operational.js` `uniqueSourceBySku` | 負值丟錯，整批同步停止 | 只擋非安全整數 |
| `src/flyingmouse/sheets-review.js` `sourceFromApprovedReviewRow` | 負值視為無效核准而跳過 | 只擋非安全整數 |
| `src/flyingmouse/inventory-writeback.js` `safeNonNegativeInteger` | 負值丟 `INVALID_PART`，到貨回寫卡在「需人工確認」 | 改為 `safeStockInteger`，接受負值 |
| `src/flyingmouse/sheets-writeback.js` 佇列 J/K 欄 | `optionalNonNegativeInteger` | 改為 `optionalStockInteger` |

commit b5245f2 當初加夾值，目的是「負庫存不可以阻斷商品名稱、規格與圖片同步」。
那個目的靠「接受負值」一樣達成，而且不必謊報庫存。

### 順帶修掉的 `Number()` 寬鬆解析

原本 `safeNonNegativeInteger` 用 `Number(value)`，而 `Number(null)`、`Number('')`、
`Number(false)`、`Number([])` 全都是 `0` 且通過 `Number.isSafeInteger`。
也就是飛鼠 API 改欄位名導致 `stock` 變成 `null` 時，回寫會把它當成「庫存 0」，
接著以 `0 + 到貨量` PUT 回去，把真正的庫存抹掉。

`safeStockInteger` 與 `optionalStockInteger` 改成只接受 `number` 或 `/^-?\d+$/` 字串，
其餘一律丟錯。到貨量仍然必須是正整數，這點沒變。

### 到貨回寫在負庫存下的行為

`expectedStock(current, received)` 一律是 `current + received`，但**目標為負時不送 PUT**：

- −1 收到 2 件 → 1，照常回寫。
- −5 收到 5 件 → 0，照常回寫。
- −5 收到 2 件 → −3，丟 `NEGATIVE_TARGET_STOCK` 轉「需人工確認」，不呼叫 PUT。

理由是飛鼠**讀**得出負庫存，但**存**檔會把負數正規化為 `0`（2026-10-29 由使用者確認）。
送 −3 會被存成 0，等於無聲抹掉 5 個超賣帳，而且驗證 GET 必定對不上。
補貨量補不滿超賣是人要決定的事，不是自動化該猜的。

PUT 之後的驗證仍然要求精確等於目標值，不因負值放寬。

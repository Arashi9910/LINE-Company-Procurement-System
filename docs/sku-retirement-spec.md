# 貨號汰換對應規格

## 1. 問題

飛鼠上重新上架會產生全新的貨號，舊貨號在 SKU主檔 被標成「不可補貨」。但舊貨號上的
需求不會消失：

2026-11-02 的正式資料，28 筆要叫貨中有 7 筆是停用貨號，其中 4 筆合計 5 件未寄
（客戶下單還沒出貨）。這些列出現在缺貨清單上卻不能勾選，而真正該補的新貨號
因為沒有銷售紀錄而看起來不缺。

床上升降折疊電腦桌是第一個案例：舊的 8 個貨號全部重新上架成 `830941146509-*`。

## 2. 為什麼不自動比對

款式（`【一般款】`／`【品質升級款】`／`【一般加大款】`）兩邊完全一致，看起來可以推導，
但顏色不行：

| 舊 | 新 |
| --- | --- |
| 珍珠白 | 暖白色 |
| 胡桃色 | 胡桃木 |

這是商品個別的命名習慣，推導不出來。猜錯的後果是照著錯的顏色去叫貨，而且沒有人會發現。

> **對應一律人工填寫，程式不猜。**

## 3. 對應分頁

新增「貨號汰換」分頁：

| 欄 | 內容 |
| --- | --- |
| A 舊貨號 | 已停用的貨號，人工填 |
| B 新貨號 | 重新上架後的貨號，人工填 |
| C 備註 | 人工填，例如「2026-10 重新上架」 |
| D 狀態 | **由程式回寫**：`已套用` 或 `已擋下` |
| E 說明 | **由程式回寫**：擋下的原因 |
| F 最後檢查時間 | 由程式回寫 |

A、B、C 是人工維護的，程式只寫 D、E、F。

## 4. 折疊時機與範圍

在資料進入 `buildInventoryDashboard` **之前**折疊，計算本身完全不改。
`applySkuRetirement` 是純函式，獨立可測。

會搬的：

- **未寄**（`orderQuantities` 的 processing／preparing）：舊 → 新相加。
  客戶在等的貨要從新貨號出，所以需求屬於新貨號。
- **近 30 天售出**（`recentUnits`）：舊 → 新相加。
  同一件商品的銷量，每筆訂單只會記在其中一個貨號下，相加不會重複計算。

**不會搬的**：

- **飛鼠庫存**：停用貨號的庫存數字不可信，而且實體貨在新貨號下。
  舊貨號庫存不為 0 就擋下整條對應，讓人去看，不要猜。
- **已叫貨未到**：採購單是下在舊貨號上的，到貨也會登記在舊貨號。
  搬過去會讓新貨號看起來有貨要到卻等不到。舊貨號還有未到量就擋下整條對應。

折疊成功後，舊貨號**不列進看板**；新貨號的備註註明數字的來源，
例如「含已汰換 069A04… 的未寄 2 件」，不讓數字無聲無息地變大。

## 5. 擋下的條件

任何一條不成立就擋下該條對應，並把原因寫回 E 欄。**擋下只影響該條，不影響整輪同步。**

- 舊貨號或新貨號空白。
- 舊貨號等於新貨號。
- 新貨號不在 SKU主檔。
- 新貨號在 SKU主檔 是「不可補貨」——指到一個也不能補的貨號沒有意義。
- 舊貨號在 SKU主檔 仍是「可補貨」——還在用的貨號不該被汰換，多半是填錯。
- 舊貨號的飛鼠庫存不為 0。
- 舊貨號還有已叫貨未到的量。
- 同一個舊貨號出現多次。
- 鏈狀對應（A→B 且 B→C）：只接受一層，避免環與順序問題。

多個舊貨號指到同一個新貨號是允許的，數字相加。

## 6. 驗收

- `npm test`、`npm run lint`、`npm run build` 全過。
- 新增測試涵蓋：
  - 未寄與近 30 天售出相加到新貨號，舊貨號不出現在結果裡。
  - 飛鼠庫存不為 0、仍可補貨、還有未到量、鏈狀、自我對應、新貨號不存在或不可補貨
    這幾種都擋下，且只擋該條。
  - 多個舊貨號指到同一個新貨號時數字正確相加。
  - 沒有對應分頁時行為與現在完全相同（功能可選，不影響既有部署）。
- 以正式資料試算：套用桌子那 8 條之後，要叫貨筆數與不可補貨筆數的變化符合預期。

## 7. 風險

- 這會改變看板的數字。套用前後的差異要能解釋，不然沒人敢相信看板。
  因此 D／E 欄的回寫是必要的，不是裝飾。
- 舊貨號的 30 天銷量搬到新貨號後，安全庫存會跟著變大。這是對的——需求本來就在——
  但第一次套用會看到缺口跳升，要先讓使用者知道。
